## 1. Таблица `projects` — финальная схема

Черновик, который раньше лежал в `CLAUDE.md`, уточнён в нескольких местах.

### Что изменено относительно самого первого черновика и почему

1. **`tag` — `text`, не Postgres `enum`.** Сейчас 5 значений (`Order`, `Personal project`, `Trial work`, `Team project`, `RPG map`), но это ярлык для человека, не структурная категория. `enum` требует `ALTER TYPE ... ADD VALUE` при каждом новом слове — миграция схемы ради переименования ярлыка, то самое избыточное усложнение. Если позже понадобится фильтровать по тегам программно — решается `CHECK`-ограничением или отдельной справочной таблицей, не раньше реальной потребности.
2. **`price_label` — обязательное поле всегда, не только фоллбэк при `price_amount IS NULL`.** UI печатает готовую строку "€150" один в один — держать готовую display-версию проще, чем форматировать число в валюту на фронтенде каждый раз.
3. **Добавлен `sort_order` (integer, nullable).** SQL-таблица не хранит "естественный порядок массива" — без явной колонки нечем будет управлять порядком карточек/карусели из будущей админки.
4. **Добавлен `is_featured` (boolean, default `false`)** вместо неявного "первые 5 по порядку = карусель". Иначе изменение порядка сетки случайно меняет состав карусели — это два разных решения, которые не должны зависеть друг от друга.
5. **`size_label`/`deadline_label` — обязательные текстовые поля**, `size_x`/`size_z`/`deadline_days` — числовые и nullable, на будущее (сортировка/фильтр "покажи самые крупные постройки"), но не единственный источник отображаемой строки — тот же принцип, что и с ценой.
6. **`id` (uuid) отдельно от `slug` (text, unique)** — `id` стабилен даже если slug однажды переименуют в админке, `slug` — то, что видно в URL и что уже сегодня использует `getProject(slug)`.

### SQL

```sql
create table public.projects (
  id            uuid primary key default gen_random_uuid(),
  slug          text not null unique,           -- URL-адрес: /portfolio/[slug]
  title         text not null,
  tag           text not null,                  -- ярлык-строка, не enum (см. п.1)
  summary       text not null,                  -- короткий текст для карточки/карусели
  description   text not null,                  -- длинный текст для детальной страницы

  image_url     text not null,                  -- главное фото (Supabase Storage URL)

  price_amount    numeric,                      -- null для "trial"/"personal project"/"team project"
  price_currency  text default 'EUR',
  price_label     text not null,                -- всегда есть: "€150", "trial", "team project"

  size_label    text not null,                  -- всегда есть: "250×250"
  size_x        numeric,                        -- в блоках, nullable — для будущей сортировки/фильтра
  size_z        numeric,

  deadline_label  text not null,                -- всегда есть: "1 week"
  deadline_days   numeric,                      -- nullable — для будущей сортировки/фильтра

  is_featured   boolean not null default false, -- попадает ли в hero-карусель
  sort_order    integer,                        -- порядок внутри своей группы (карусель/сетка)

  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

create index projects_slug_idx on public.projects (slug);
```

### `project_images` (галерея)

Отдельная таблица вместо JSON-массива — переменное число строк со своим порядком, а не одно скалярное значение. `on delete cascade` — как автоматическое освобождение дочерних объектов при удалении родителя (composition: проект _владеет_ своими фото).

```sql
create table public.project_images (
  id          uuid primary key default gen_random_uuid(),
  project_id  uuid not null references public.projects(id) on delete cascade,
  url         text not null,
  position    integer not null default 0,   -- порядок в галерее
  created_at  timestamptz not null default now()
);

create index project_images_project_id_idx on public.project_images (project_id, position);
```

## 2. Разные layout'ы карточки/детальной страницы — решение

**Не вводить `layout`/`template`-колонку сейчас.** Все 16 текущих проектов рендерятся сегодня одинаково — нет ни одного, который _хочет_ другой layout. Колонка-переключатель с одним фактическим значением на все строки — классический признак преждевременной абстракции.

Цена ошибки в другую сторону низкая: добавить `layout text default 'default'` потом — одна `ALTER TABLE ADD COLUMN` с дефолтом, без бэкфилла существующих строк.

Настоящая гибкость, которая реально нужна уже сегодня — не "разные шаблоны страницы", а "не у всех проектов есть все поля" (например `price: "trial"` вместо суммы). Это уже частично реализовано: `{project.gallery && project.gallery.length > 0 && (...)}` в `[slug]/page.tsx` рендерит блок галереи только если она есть. Держаться этого паттерна — **один layout, часть блоков опциональна по данным** — вместо `if (layout === 'x') return <LayoutX />` для каждого нового поля.

Когда реально накопится 2-3 проекта с принципиально другой структурой страницы (не просто отсутствие одного поля, а другой порядок/другие блоки) — тогда добавляется `layout`-колонка, а в компоненте — обычная ветка по значению (`switch (project.layout) { case 'video': ...; default: ... }`), концептуально то же самое, что полиморфизм через ветвление по типу вместо отдельных классов — на масштабе одной страницы это нормально и не требует системы шаблонов.

## 3. `reviews` и `stats` — схема (кратко)

Обе уже "table-shaped" в коде (`src/lib/reviews.ts`, `Stats.tsx`) — перенос формы 1-в-1, без изменения домена.

```sql
create table public.reviews (
  id          uuid primary key default gen_random_uuid(),
  slug        text not null unique,   -- URL: /reviews/[slug]
  name        text not null,
  role        text not null,
  flag        text not null,          -- эмодзи-флаг, как сейчас; позже можно заменить на country_code
  review_text text not null,          -- "text" — зарезервированное по смыслу имя, лучше не путать
  accent      text not null default 'orange' check (accent in ('orange', 'lime')),
  sort_order  integer,
  created_at  timestamptz not null default now()
);

create table public.stats (
  id          text primary key,        -- "orders"/"reach"/"clients" — тот же id, что и сейчас в массиве
  label       text not null,
  value       numeric not null,
  suffix      text not null default '',
  -- ⚠️ Устарело: в реализованной схеме color/bar заменены на одну колонку
  -- accent text check (accent in ('orange','lime','blue')) — конкретные
  -- tailwind-классы вернулись в Stats.tsx, потому что это вопрос дизайна,
  -- а не данных. См. миграцию 20260720190000_stats_accent.sql.
  color       text not null,           -- tailwind-класс, как сейчас ("text-orange-400")
  bar         text not null,           -- tailwind-класс ("bg-orange-400")
  updated_at  timestamptz not null default now()
);
```

`accent` — тот же случай, что и `tag` в `projects`: `text` + `CHECK` вместо `enum`, потому что значений мало и стабильно, а `CHECK` дешевле менять. `stats.id` — сознательно текстовый первичный ключ, не uuid: это константный список из трёх строк, редактируемых вручную, а не создаваемых программно — играет роль "ключа настройки", как строковый ключ в конфиге.

## 4. Миграция: локальный массив → Supabase

Ключевая идея — держаться уже существующей границы: **`getProject(slug)` уже единственная точка, через которую компоненты трогают данные проекта.** Как интерфейс в ООП — вызывающий код общается с контрактом ("дай мне проект по slug"), а не с конкретной реализацией. Миграция — замена _реализации_ функции, а не переписывание всех мест, где она вызывается.

Сегодня:

```ts
export function getProject(slug: string) {
  return projects.find((p) => p.slug === slug);
}
```

После:

```ts
export async function getProject(slug: string) {
  const { data } = await supabase
    .from("projects")
    .select("*, project_images(*)")
    .eq("slug", slug)
    .single();
  return data;
}
```

Название функции и файл не меняются — меняется только то, что внутри.

### Что реально нужно тронуть

Главное отличие: `.find()` в массиве — синхронная операция (мгновенная, в памяти), запрос к Supabase — асинхронная (сеть, БД). Любое место, которое сегодня зовёт `getProject`/`projects` синхронно, должно стать `async`/дождаться `await`.

- **`src/app/(site)/portfolio/[slug]/page.tsx`** — уже частично готов: `ProjectPage` уже `async`. Добавить `await` перед `getProject(slug)`. `generateStaticParams()` — сегодня синхронная, нужно сделать `async` и заменить на запрос списка всех `slug` (Next.js поддерживает `async generateStaticParams` нативно). `generateMetadata` уже `async` — там просто не хватает `await` перед вызовом.
- **`src/app/(site)/portfolio/page.tsx`** — сегодня не `async`, читает `projects` напрямую. Нужно сделать `async function PortfolioPage()` и получать список через новую функцию `getAllProjects()` с `await`. Компонент серверный (без `"use client"`) — асинхронные Server Components в App Router поддерживаются "из коробки".
- **`src/components/PortfolioHero.tsx`** — клиентский компонент (`"use client"`), принимает готовый `projects: Project[]` через пропс — трогать не нужно. Данные приходят уже загруженными сверху, из `portfolio/page.tsx`. Граница "серверная страница один раз получает данные, дочерние клиентские компоненты просто их рисуют" уже правильная — асинхронность БД не просачивается туда, где в ней нет нужды.
- **`src/lib/projects.ts`** — здесь появится `getAllProjects()`, чтобы прямой импорт сырого массива не был размазан по нескольким местам (`portfolio/page.tsx`, `[slug]/page.tsx`'s `generateStaticParams`, `RecentProjects.tsx`) — все обращения идут через `getProject(slug)` и `getAllProjects()`.
- **`src/lib/reviews.ts`** и `src/app/(site)/reviews/[slug]/page.tsx` — тот же паттерн, что и у портфолио: `getReview(slug)` уже единственная точка доступа, миграция аналогична.

### Порядок действий при реальной миграции

1. Создать таблицы в Supabase по схеме из раздела 1/3.
2. Разово перенести существующие строки (INSERT-скрипт или вручную через Table Editor — их немного).
3. Переписать `getProject`/добавить `getAllProjects` в `projects.ts` (аналогично для `reviews.ts`) — заменить `.find()`/прямой доступ к массиву на Supabase-запросы.
4. Пройтись по местам выше, сделать их `async`, добавить `await`.
5. `Project`/`Review` тип — привести в соответствие с формой строки из БД (`image` → `image_url`, `gallery?: string[]` → `project_images: {url, position}[]`) — один разовый рефакторинг типа, не постепенный.

## 5. RLS — что важно сейчас, что нет

Коротко, потому что сегодня нет админки и нет пользовательской авторизации — все данные публичные и только для чтения.

- **Нужно сделать при создании таблиц:** включить RLS на всех таблицах и сразу дать политику публичного чтения:
  ```sql
  alter table public.projects enable row level security;
  create policy "public read" on public.projects for select using (true);
  ```
  (аналогично для `project_images`, `reviews`, `stats`). Причина делать это сразу: Supabase по умолчанию блокирует anon-доступ, если RLS включён без политик — сайт с самого начала мог бы просто не получать данные. Не включать RLS вообще — тоже плохая отправная точка, таблица по умолчанию открыта без ограничений.
- **Не нужно делать сейчас:** политики на `insert`/`update`/`delete` — есть смысл писать только когда появится реальный субъект действия (админ через Supabase Auth в Этапе 3, покупатель в Этапе 4). Писать write-политики под несуществующего пользователя — гадать вслепую, почти наверняка придётся переписывать.
- **На будущее (Этап 3):** write-доступ разумнее давать через service-role ключ на серверной стороне (Server Actions/API routes), защищённый проверкой сессии Supabase Auth на уровне приложения — RLS становится вторым рубежом защиты, не единственным. Стандартный паттерн для Supabase-проектов с собственной админкой, решать подробнее при подходе к Этапу 3.

## 5.1. `profiles` — профиль пользователя (реализовано 2026-07-24)

Миграция `20260724120000_profiles.sql`. Расширение `auth.users` один-к-одному по `id` (`references auth.users(id) on delete cascade`). Держит «наше» про пользователя: `display_name` (публичный ник, уникальный **регистронезависимо** через `unique index on lower(display_name)`), `first_name`/`last_name` (личное, на будущее), `avatar_url` (аватар, на будущее), `is_creator` (флаг, Этап 4), `discord` (будущее), `created_at`/`updated_at`. **Email не дублируем** — он в `auth.users`, копия рассинхронизировалась бы.

- **Автосоздание:** триггер `on_auth_user_created` → функция `handle_new_user()` (`security definer`, `search_path=''`) вставляет строку профиля при регистрации, ник — из `raw_user_meta_data->>'display_name'` (фоллбэк — часть email до `@`). Занятый ник → уникальный индекс откатывает регистрацию (серверная проверка «ник занят»).
- **RLS:** пользователь видит и правит только свою строку (`auth.uid() = id`). Публичного чтения нет намеренно — добавим для полей креатора, когда появится маркетплейс. INSERT-политики нет: строки создаёт только триггер.

## 5.2. `products` и магазин — схема (актуально на 2026-09-06)

Раньше этот документ описывал только портфолио; схема магазина жила в самих миграциях. Фиксирую здесь, потому что за 2026-07-30 она изменилась сильнее всего.

`products` (`20260722120000`, дополнена позже):

- **Деньги — целое число центов** (`price_cents`), плюс готовая строка для показа (`price_label`). UI валюту не форматирует.
- 🟢 **Состояние — ОДНА колонка `state`** (миграции `20260815130000`, `20260815140000`, `20260815160000`). Перечень: `pending / rejected / live / hidden / suspended / deleted`, разрешённые переходы стережёт триггер `guard_product_state`, новая карта всегда начинается с `pending` (`guard_product_insert`). Правила при работе с ней:
  - **Писать только в `state`.** Старые `is_published` / `deleted_at` / `hidden_by` теперь считает триггер `sync_legacy_product_flags` — запись в них затрётся.
  - **Что можно, а что нет, знает база**, а не обработчик: новый переход — правка триггера, а не ещё одна проверка в коде.
  - Видимость на витрине = `state = 'live'` **и** активный статус автора (`creator_active`): отзыв креаторства уносит карты, возврат статуса возвращает их туда, где они были.
  - Удаление мягкое у обеих сторон, различает их `deleted_by` (`20260815150000`).
- 🟢 **Старых колонок больше нет** (шаг 2, миграция `20260816120000`). `is_published` / `deleted_at` / `hidden_by` / `status` удалены вместе с триггером синхронизации; политика витрины стала `state = 'live' and creator_active`. У карты одно описание состояния, а не пять.
- `category` — реальная колонка (`20260730150000`, восемь значений). У строк, заведённых до неё, пусто, и тогда работает фоллбэк `deriveCategory(slug)` в `src/lib/products.ts`. **«free» — не категория:** бесплатность определяется ценой 0, иначе платная карта могла бы оказаться под тегом Free.
- 🟢 **Характеристики карты** (`20260821130000`): `mc_versions`, `game_modes`, `themes`, `file_formats`, `tags` — наборы (`text[]`); `map_size` — одно значение; плюс `file_size_bytes` (считается из файла, автор не вводит) и `published_at`. Длину наборов и строк стережёт `products_specs_len` через `array_within`. **Словари значений живут в коде** (`src/lib/product-specs.ts`): база стережёт объём, код — вкус, и пополнить список тем можно без миграции.
- 🟢 **Тип карты — НАБОР до трёх** (`map_types text[]`, миграция `20260906120000`). Заводился 21.08 одним значением с доводом «карта бывает чем-то одним» — живой каталог довод опроверг: спавн с городом честно является и тем и другим. ⚠️ **Потолок в три — это смысл, а не защита от переполнения:** карта, помеченная всеми типами, не описана никак. Стоит он в базе (`products_map_types_len`), потому что запись идёт из браузера напрямую. Старая колонка `map_type` пока жива и читается запасным путём — **снести её отдельной миграцией ПОСЛЕ деплоя**, как делали со `state`.
- 🔴 **Чего в схеме нет, хотя запланировано:** внешние ссылки (превью-видео, Discord автора), текстовые отзывы на карту, просмотры карты по аккаунту.
- `rejection_reason` (текст автору) и `rejection_flags` (`text[]`, коды пунктов из `src/lib/rejection.ts`).
- `creator_id` → `profiles(id)`, `on delete set null`: удаление аккаунта не должно уносить проданные карты — на них ссылаются заказы.
- `file_path` — путь в **приватном** бакете `product-files`. Прямой ссылки не существует, только подписанная на час (`signedDownloadUrl`).

`product_images` (`20260727120000`) — галерея отдельной таблицей, как `project_images` у портфолио. Обложка живёт НЕ здесь, а в `products.image_url`; эта таблица только дополнительные кадры, порядок — `position`. Заменяется атомарно функцией `replace_product_images` (`20260730180000`): раньше это были `delete` + `insert` двумя запросами, и между ними у товара было ноль картинок.

### RLS магазина — по ролям

| Кто            | Что может                                                                             |
| -------------- | ------------------------------------------------------------------------------------- |
| аноним         | читать только `is_published` товары и картинки к ним                                  |
| креатор        | создать свою карту, читать и править **свои** (в любом статусе), править свою галерею |
| владелец сайта | всё, но **только через сервер** под служебным ключом                                  |

Четыре вещи, которые эта таблица не показывает, а знать их обязательно:

1. **`INSERT ... RETURNING` требует ещё и SELECT-политику.** `.insert().select()` не сработает, если политика чтения не пускает к только что созданной строке. На этом сломалась первая версия загрузки: черновик не опубликован, а читать «только опубликованное» — единственное, что было разрешено.
2. **Публиковать себя сам креатор не может.** Политика правки разрешает менять свою строку целиком, поэтому состояние защищают триггеры, а не политика: `guard_product_state` сверяет разрешённость перехода, а `guard_product_author_edit` возвращает конечному пользователю все поля состояния из старой строки и сам решает, отправить ли карту на повторный разбор (снятая и отклонённая — в очередь, живая с подменённым файлом — тоже).
   **Список защищаемых полей обязан быть полным.** До 2026-08-16 в нём не было `creator_active`, и лишённый статуса креатор мог вернуть свои карты на витрину одним запросом из консоли: `update products set creator_active = true`. Форма такого не отправляет, но форма тут и ни при чём — сессия и публичный ключ лежат у пользователя.
3. **`is_admin` тоже защищён триггером** (`protect_is_admin`), потому что «правь свою строку» иначе позволяло бы выдать админку себе из браузера. **То же самое у `is_creator`** (`20260814120000`) — иначе креаторство выдавалось бы себе одним запросом из консоли.
4. **Вставку с готовым состоянием база не примет** (`guard_product_insert`, 2026-08-15). До этой миграции карту можно было создать напрямую из браузера сразу `live`, минуя модерацию — дыра существовала с момента открытия загрузки.

### Бакеты Storage

| Бакет            | Публичный | Что внутри                                 | Политики                                                           |
| ---------------- | --------- | ------------------------------------------ | ------------------------------------------------------------------ |
| `avatars`        | да        | аватары                                    | чтение всем, запись в свою папку                                   |
| `product-images` | да        | обложки, галереи, картинки внутри описаний | чтение всем, INSERT в свою папку                                   |
| `product-files`  | **нет**   | файлы карт                                 | ⚠️ **записи из браузера нет вовсе** (с 2026-09-11); чтение — подписанной ссылкой с сервера |

DELETE-политик нет ни у одного и не должно быть: иначе креатор смог бы удалить чужой файл. Уборка неиспользуемых объектов идёт служебным ключом через `/api/creator/cleanup-storage`.

⚠️ **`product-files` — первый бакет, полностью закрытый от браузера (2026-09-11).**
Политика `product-files insert own folder` снята миграцией
`20260911120000_map_file_gateway`. Писать туда может только служебный ключ, то
есть наш обработчик `/api/creator/upload`: он проверяет права, лимит частоты,
размер и расширение, **сам строит путь** и выдаёт одноразовый токен
(`createSignedUploadUrl`), а после загрузки читает первые байты объекта и
сверяет сигнатуру. Разбор — [`ARCHITECTURE.md`](ARCHITECTURE.md) § 5.3.

⚠️ **`product-images` и `avatars` так НЕ закрыты** — в них браузер пишет
по-прежнему. Граница проведена по бакету сознательно: доказательством переезда
служит снятая политика, а снять половину политики нельзя.

## 5.3. Схема `ops` — служебное, наружу не отдаётся (2026-08-22)

Отдельная схема, а не таблица в `public`. Причина: PostgREST отдаёт наружу
схему `public`, и таблица там стала бы endpoint'ом ещё до того, как мы решим,
нужен ли он.

### `ops.applied_migrations` — журнал прогонов

| колонка      | тип                | смысл                         |
| ------------ | ------------------ | ----------------------------- |
| `version`    | `text` primary key | имя файла миграции без `.sql` |
| `applied_at` | `timestamptz`      | когда прогнали в ЭТОЙ базе    |

**Пишет её не человек, а сам прогон:** каждый файл миграции заканчивается
строкой `insert into ops.applied_migrations (version) values ('…') on conflict
do nothing;` — правило и обоснование в [`RULES.md`](RULES.md) → «Миграции».
Заполнять руками нельзя: смысл журнала ровно в том, что запись появляется
только при исполнении.

**RLS включён, политик нет ни одной** — это значит «никому», а не «всем».
Схема `ops` в Exposed schemas не перечислена, то есть снаружи таблицы нет и
так, но «не перечислена» — это НАСТРОЙКА ПРОЕКТА, а не свойство базы: её
меняют галочкой. Защита, живущая в чужих настройках, — не защита.

Приложение в эту схему не ходит и ходить не должно: она для человека в
SQL-редакторе.

**Спросить базу:**

```sql
select version, applied_at from ops.applied_migrations order by version;
```

Журнал начинается с `20260822120000` и о прошлом не знает намеренно. Всё, что
старше, прогнано на обеих базах — проверено зондами 2026-08-22.

### `ops.rate_events` — счёт для лимитов на `/api/*` (2026-08-23)

| колонка      | тип                     | смысл                                        |
| ------------ | ----------------------- | -------------------------------------------- |
| `id`         | `bigserial` primary key |                                              |
| `bucket`     | `text`                  | что сделали: `checkout`, `admin-announce`, … |
| `actor`      | `text`                  | id аккаунта того, кто сделал                 |
| `created_at` | `timestamptz`           | когда                                        |

**Строка = одно совершённое действие, а не счётчик со сбросом.** Окно
скользящее («сколько за последний час»), и посчитать его иначе нельзя.
Счётчик, обнуляемый в начале часа, даёт известную дыру — двойной лимит на
стыке: полный расход в 10:59 и ещё один полный в 11:01.

**Пишется только через `public.consume_rate_limit(bucket, actor, limit,
window_seconds)`** — функция в `public`, потому что таблица в `ops`, а `ops`
наружу не выставлена и через PostgREST её не позвать. Функция
`security definer`, `execute` отозван у `public/anon/authenticated` и выдан
только `service_role`: **Postgres выдаёт execute роли PUBLIC по умолчанию**,
и без явного `revoke` её звал бы кто угодно из консоли браузера.

Возвращает **число секунд ожидания**: `0` — можно, больше нуля — столько
ждать (идёт в заголовок `Retry-After`). Внутри берёт
`pg_advisory_xact_lock` на пару (bucket, actor), иначе два одновременных
запроса одного человека оба видят «использовано 9 из 10» и оба проходят.

**Сколько чего можно — в коде** ([`src/lib/rate-limit.ts`](../src/lib/rate-limit.ts)),
не в базе: лимит меняется чаще схемы, и правка числа не должна требовать
миграции. База при этом остаётся местом, где решение исполняется.

⚠️ **Кого здесь нет намеренно:** `/api/stripe/webhook` (его дёргает Stripe и
повторяет при отказе — лимит означал бы «деньги взяты, карта не выдана») и
`/api/view` (свой лимит, и считает по IP, потому что туда ходят
неавторизованные).

Уборка: свои протухшие строки удаляет сам вызов, а примерно каждый сотый
подметает всё старше суток. `pg_cron` не включён — когда появится трафик,
эта строка заменяется расписанием.
