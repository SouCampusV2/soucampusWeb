# Обязательные правила сессий — SouCampus builds

Правила, которые действуют **каждую сессию** и имеют приоритет над удобством/скоростью. Читать вместе с [`CLAUDE.md`](../CLAUDE.md). Дизайн-правила — в [`DESIGN.md`](DESIGN.md).

## Как работать со мной (калибровка объяснений)

Мой уровень:
- Знаю HTML/CSS, немного JS. Синтаксис слабый — не напишу класс на JS/Python с нуля.
- Хорошо понимаю архитектурные концепции (наследование, полиморфизм, ООП) — теорию знаю.
- Есть опыт с FlutterFlow (low-code) и немного с API.
- Не уверен, что могу писать код «с нуля» сам — нужна помощь на уровне синтаксиса, а не только архитектуры.

Как объяснять код:
- **Не считать, что я знаю синтаксис JS/TS/React** — показывать конкретный код, а не только «напиши функцию, которая...».
- Архитектурные термины (компонент, состояние, пропсы, наследование) — можно смело, я пойму через аналогии с ООП.
- На первых порах — больше готового кода с объяснением, что каждая часть делает; потом постепенно давать писать самому.
- Не бояться повторять базовые вещи синтаксиса несколько раз, пока не закрепится.
- Объяснять простым языком; формат объяснений — реальный код из проекта + почему именно так, без пересказа документации.

## Правила разработки

- Простые решения там, где уместно; не усложнять архитектуру без причины.
- Сначала рабочая версия, потом улучшения. Изменения — постепенно и с документированием.
- **Приоритет производительности:** сайт должен грузиться максимально быстро (оптимизация картинок, минимум лишнего JS на клиенте — см. Server/Client Components).
- Для медленных/асинхронных блоков (загрузка данных, изображений) — **skeleton-плейсхолдеры**, не пустой экран и не спиннеры.
- **Весь видимый на сайте текст — на английском.** Комментарии в коде и `.md`-файлы остаются на русском (внутренняя документация, посетители её не видят).

## API и backend

- **Плоский CRUD** (достать/записать строки) — через **Supabase SDK / авто-REST (PostgREST)**, свой эндпоинт не писать. RLS защищает, кода меньше.
- **Действие/своя логика** (оплата, вебхук, счётчик, гейты, админ-операции) — свой **Next.js Route Handler** в `src/app/api/*`, RPC-стиль: `POST`, JSON внутрь/наружу, честные статус-коды (`400`/`404`/`500`), проверка входа вверху обработчика.
- Обход RLS/секреты (`supabase-admin.ts`, service-role ключ) — **только на сервере**, никогда с клиента.
- Отдельный самостоятельный backend-сервис — **не заводить без конкретной нагрузки-триггера** (обработка файлов/картинок, массовая рассылка, тяжёлый крон); держать монолит и модульный слой `src/lib/*`. Подробнее — `ROADMAP.md` → «Отдельный backend».

## Миграции (выучено 2026-08-15, оба правила ценой падений)

- **Порядок: миграция → код, а не наоборот.** Сначала прогнать на preview, убедиться, что работает, и только потом пушить код, который на неё опирается. Нарушение выглядит как «сайт сломался на ровном месте»: код спрашивает у базы то, чего там ещё нет.
- **После миграции, добавляющей или переименовывающей колонку, выполнить `notify pgrst, 'reload schema';`** в том же SQL-редакторе. PostgREST держит собственный кэш схемы: в SQL-редакторе колонка уже есть, а сайт продолжает отвечать `column ... does not exist`, и это выглядит как «миграция не прогналась».
- **Тот же порядок на проде:** миграции → `notify pgrst` → мёрж в `master`. Между мёржем и деплоем нет паузы, в которую можно успеть.
- **`create or replace view` умеет только ДОПИСЫВАТЬ колонки в хвост** (выучено 2026-08-21). Имена и порядок уже существующих обязаны совпасть один в один: новая колонка, поставленная в середину «по смыслу», читается позиционно и роняет прогон с `42P16: cannot change name of view column "X" to "Y"`. Расставить красиво можно только через `drop view`, а он сносит и `grant`, и всё, что на представление ссылается. **Порядок колонок в представлении не значит ничего** — код выбирает их по имени, — поэтому новое всегда идёт последним.
- **Миграцию писать перезапускаемой.** `add column if not exists`, `drop constraint/index if exists` перед созданием, заполнение только там, где значения ещё нет. Прогон падает на середине чаще, чем хочется (см. правило выше), и тогда единственный дешёвый выход — запустить файл целиком заново.
- **Правило переходов живёт в базе.** Если у сущности есть состояния — их перечень и разрешённые переходы описываются триггером, а не проверками в обработчиках. Проверку в коде можно обойти запросом мимо него, а состояний, которых не должно существовать, не должно быть возможно записать (пример — `products.state`, миграция `20260815130000`).
- **Каждая миграция последней строкой записывает себя в журнал** (заведён 2026-08-22, миграция `20260822120000_migration_log`). В конец файла:
  ```sql
  insert into ops.applied_migrations (version) values ('ИМЯ_ФАЙЛА_БЕЗ_SQL')
  on conflict do nothing;
  ```
  **Зачем:** CLI не заведён, прогон идёт руками в SQL-редакторе и следа не оставляет — ни в git (там файл, а не факт исполнения), ни в базе. Ответ на «что уже на проде» давала память, и 22.08 она соврала: `20260821160000` числилась ожидающей в двух документах, а была прогнана. **Список в документации эту болезнь не лечит, он ею болен** — список у нас был, его вели, он всё равно разошёлся с базой. Поэтому запись делает сам прогон, а не человек после него.
  **Почему в конце, а не в начале:** работает при любом поведении редактора. Гонит транзакцией — упавший прогон откатит и запись; гонит по запросу — выполнение остановится на упавшем месте и до `insert` не дойдёт. Наполовину прогнанная миграция не пометится прогнанной никогда.
  **Проверить базу:** `select version, applied_at from ops.applied_migrations order by version;` и сравнить с `ls supabase/migrations/`. Журнал начинается с `20260822120000` и о прошлом не знает намеренно — задним числом его не заполняли, потому что вписать «прогнано» по памяти это ровно та ошибка, от которой он заводится. Всё, что старше, прогнано на **обеих** базах (проверено зондами 2026-08-22).

## Отладка (выучено дорого, каждое — ценой потерянного дня)

- **Прежде чем чинить гипотезой — поставь три строчки лога.** За один день 2026-08-15 пять правдоподобных диагнозов оказались неверными подряд; консоль ответила за один раунд. Правдоподобие догадки о её верности не говорит ничего.
- **Починил место — проверь класс.** Дата без явной локали, `router.refresh()` после `await`, замороженный `useState(props)` — каждая из этих ошибок жила не в одном файле, а в нескольких сразу. Найдя одну, сразу ищи остальные копии: `grep` по образцу дешевле, чем второй заход через неделю. (Свежий пример 2026-08-19: хвост обещал две даты без локали, в коде их было семь.)
- **На тач-экране `hover` не наступает НИКОГДА — меню на `group-hover` там не существует** (выучено 2026-08-26). Выпадашка профиля в навбаре открывалась чистым CSS, без состояния; на телефоне это означало, что Log out, My profile и My purchases недоступны ниоткуда, и полтора месяца этого никто не замечал, потому что на десктопе всё работает. ⚠️ Проверять при КАЖДОМ новом меню: если оно открывается только по наведению, на телефоне его нет.
- **`SUBSCRIBED` ничего не доказывает.** Канал Realtime рапортует об успешной подписке и без токена — просто не отдаёт ни одной строки, потому что RLS-политика написана для `authenticated`. Ноль событий, ноль ошибок, и выглядит это как «уведомления не работают».

## Чужие сервисы (выучено 2026-08-25, вход через Google)

- **`Redirect URLs` в Supabase сверяются ЦЕЛИКОМ**, вместе с параметрами запроса. Не совпало — Supabase **молча подставляет `Site URL`**, без ошибки и без предупреждения: человек приезжает на корень сайта с `?code=` в адресе, а наш `/auth/callback` не выполняется вовсе. ⚠️ Хуже всего момент: отказ виден **после** того, как человек уже согласился у Google. Маска `/auth/callback**` покрывает и `?next=` Google-входа, и `?next=/reset-password` сброса пароля. Список нужен в **обоих** проектах, вместе с `localhost:3000` и `3001`.
- **«Вроде работает» — не доказательство.** Клиент `supabase-js` сам подхватывает `?code=` с любой страницы и меняет его на сессию. То есть вход выглядит успешным, хотя наш колбэк не отработал и вся его логика пропущена. Тот же класс, что «`SUBSCRIBED` ничего не доказывает».
- **Внешний вход перезаписывает `user_metadata` при КАЖДОМ входе.** Google кладёт туда свою фотографию и имя, затирая то, что положили мы. ⚠️ Если что-то в `user_metadata` — наш кэш из БД, его надо **заново приводить к базе после входа**. Источник правды — таблица, метаданные лишь её копия.
- **Чужую картинку по ссылке не присваиваем.** Аватар из Google лежит на `googleusercontent.com`, а профили публичны — значит браузер каждого посетителя ходил бы за ней к чужому серверу. То же правило, по которому ограничиваем `img src` в описаниях карт, и то, что обещано в `/privacy`.

## Маршруты и переезды страниц (выучено 2026-08-28, ценой недели)

- **Правило-редирект с параметром съедает ВСЁ, что подходит под параметр.**
  `{ source: "/creator/:username" }` ловит и `/creator/upload`: `:username` —
  это любой односегментный адрес. Форма загрузки карты после такого правила
  не открывалась **семь дней**, отдавая 404 профиля с ником «upload».
  ⚠️ **Редиректы выполняются РАНЬШЕ маршрутизации** — существующая страница
  не получает шанса отрисоваться, поэтому «файл на месте и код верный»
  ничего не значит. Добавляя правило с параметром, перечисли всё, что уже
  живёт под этим префиксом.
- **Правила `next.config.ts` не покрыты ничем.** Тест
  `isMarketplaceRoute("/creator/upload")` проходил всю неделю, пока адрес
  отдавал 404: он спрашивает, какой рисовать навбар, а не открывается ли
  страница. Проверка, отвечающая на соседний вопрос, создаёт ложное
  спокойствие. Открывается ли адрес — проверяется запросом к собранному
  приложению (`next start` + `curl -I`), и это стоит одной команды.
- **Комментарий в одном файле не защищает адрес, который ломают в другом.**
  В `marketplace-routes.ts` прямо стояло «`/creator` остаётся ради
  `/creator/upload`» — написанное в тот же день, что и роковой редирект.
  Знание было, и оно не помогло: защищает только проверка, стоящая на пути
  правки.
- **Переезд страницы — это и все стрелки, ВЫХОДЯЩИЕ из неё.** В тот же день
  переехавшая форма получила четыре исправленных входа, а кнопка Cancel в ней
  осталась указывать на `/resources` — та у не-креатора сама перекидывает на
  витрину, и отмена загрузки заканчивалась на главной магазина. Проверять обе
  стороны: чем в страницу входят и куда она выпускает.

## Проверки, которые делаются руками

- **Проверка, которую не делают, ничего не проверяет** (выучено 2026-08-28).
  Раздел ручного чек-листа по лимитам частоты пролежал непройденным **пять
  сессий подряд** — не по лени, а потому что каждый пункт требовал открыть
  консоль браузера и набрать по памяти нужный вызов. Переписанный скриптом
  (`npm run check:limits`), он выполняется за десять секунд. ⚠️ Прежде чем
  оставлять пункт в `TEMP.md`, спроси: его не делают, потому что не дошли
  руки, или потому что он неудобен настолько, что не дойдут никогда?
- **Живую базу проверяет скрипт, а не `npm test`.** Права Postgres,
  скользящее окно, RLS — это поведение базы, а не чистых функций; мок ответил
  бы ровно то, что мы в него заложили, и подтвердил бы любую нашу ошибку.
  Такие проверки живут в `scripts/` и вне CI (`check:views`, `check:limits`).
- ⚠️ **Права на новую функцию в `public` выдаются САМИ.** Postgres даёт
  `execute` роли PUBLIC по умолчанию; `revoke` в миграции — единственное, что
  это снимает, и проверять его надо отдельным тестом. Не сработал — функция
  открыта всему интернету, а сайт выглядит полностью исправным.

## Next.js — то, что ловит только сборка

- **Файл с `"use server"` экспортирует ТОЛЬКО async-функции.** Обычная константа рядом с ними роняет сборку. ⚠️ `npx tsc --noEmit` этого не видит — видит только `npm run build`. Выучено 2026-08-25 на имени cookie.
- **`proxy.ts` живёт в Edge** и не должен тянуть `next/headers` и прочее серверное. Общее с ним выносить в нейтральный модуль — тот же приём, что `notification-shape.ts` и `comment-shape.ts`.
- ⚠️ **Отсюда правило прогона проверок:** `tsc` и `lint` не заменяют `npm run build`. Трогал роуты, серверные действия или proxy — гоняй сборку, иначе сломанное уедет в пуш.

## Секреты

- Хранить секреты в переменных окружения. Не публиковать токены и ключи в репозитории.
- **`NEXT_PUBLIC_*` вшиваются в бандл на сборке**, а не читаются при запуске. Смена значения требует пересборки, и «Redeploy» с Build Cache её может не дать. Поэтому же новые значения не подхватываются перезапуском (выучено 2026-08-15: в Preview три недели стояли ПРОДОВЫЕ значения, и `dev` спрашивал прод-базу).

## Git

- **Автор коммитов — только пользователь. Без соавторства ИИ в коммитах** (никаких `Co-Authored-By`).
- **Воркфлоу через ветку `dev`:** разработка/контент коммитятся в `dev`, пушатся, проверяются на Vercel Preview (стабильная ссылка: `https://soucampus-builds-git-dev-sou-campus.vercel.app`), и только потом мёржатся в `master` (прод, автодеплой на `soucampus.online`).
- Не пушить мелкие правки в `master` напрямую. Локальный `npm run dev` — для быстрых итераций; `dev`/Preview — для сверки перед мёржем.
- Мёрж в `master` — **отдельное осознанное действие** после мини-теста на Preview, не часть рутинного коммита/`wrap-day`.
- Правило миграций Supabase: новую миграцию сначала прогонять на preview-базе, только потом на проде.

## Юридическое (действующие решения)

- **Cookie-баннер не делаем (решено 2026-07-20).** На сайте одна своя cookie — номер посетителя для счётчика (`scv_visitor`, `httpOnly`, подписана). Только своя cookie, никакой межсайтовой слежки/передачи третьим лицам, наружу — только агрегат, IP не хранится → набор условий, при котором регуляторы (CNIL и др.) выводят измерение своей посещаемости из-под требования согласия. Срок жизни сокращён до 13 месяцев. Vercel Analytics работает без cookie. Пересмотреть при написании ToS (Этап 4). Не юридическая консультация; трактовки по странам различаются.
- **Terms of Service** (условия фриланс-заказов на Minecraft-карты) — отложено, ближе к запуску магазина/приёму заказов (Этап 4). Формула цены уже задокументирована на `/terms#pricing` — это не полноценный ToS, а самостоятельный живой раздел.
