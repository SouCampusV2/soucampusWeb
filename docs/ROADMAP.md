## Цель проекта

Современный сайт-портфолио, который вырастает в полноценный продукт, и одновременно — практическая площадка для обучения веб-разработке.

Как продукт:
- портфолио с работами и описаниями;
- отдельные страницы «кто я» и контакты;
- магазин цифровых товаров (Minecraft-карты);
- панель администратора для управления контентом и товарами.

Как учебный проект — освоить на реальном деле:
- современную веб-разработку (Next.js, TypeScript, Tailwind, Supabase, Vercel, CI/CD, Docker и далее — более сложную архитектуру);
- архитектуру приложений;
- работу с БД и авторизацией;
- деплой и основы DevOps;
- использование AI-агентов в реальном процессе разработки.

## Принцип работы

- Сначала рабочий сайт-портфолио, потом раздел портфолио и отдельные страницы, и только потом магазин, авторизация, сессии, оплата, админка.
- Не пытаться сделать всё сразу; делать поэтапно, чтобы проект всегда был рабочим и его можно было показать.
- Сначала простая рабочая версия, потом улучшения.
- Учиться на реальном проекте, а не только на теории.
- Сложное — разбивать на маленькие шаги.

## Рекомендуемый стек и почему

- **Frontend:** Next.js (App Router) + TypeScript + Tailwind CSS — хороший старт для современного сайта.
- **Backend / данные:** Supabase (Postgres) — проще, чем поднимать свой backend с нуля; PostgreSQL как зрелая основа на будущее.
- **Авторизация:** **Supabase Auth** (решено, не Auth.js) — раз БД уже на Supabase, это одна система вместо двух, меньше ручной возни с JWT/сессиями. Интеграция через Supabase JS SDK прямо в Next.js (Server Actions / API routes), отдельный backend на Python не нужен. Свою auth с нуля не делаем: хеширование паролей, сессии, refresh-токены, восстановление доступа, безопасность — много тонкостей, готовое решение снижает риск ошибок.
- **Оплата:** Stripe.
- **Деплой:** Vercel — удобная PaaS под Next.js: подключаешь GitHub, пушишь, платформа сама собирает и разворачивает. Не заменяет VPS полностью, но идеален для старта, preview и API. Hostinger VPS — позже, когда понадобится свой сервер / Docker / больше контроля.

Общая логика выбора: готовые решения по данным и авторизации ускоряют разработку и снижают риск ошибок; Vercel удобен для демонстрации и обучения workflow; проект потом масштабируется (Docker, CI/CD, облако, API, админка, аналитика).

## Архитектурный подход

Простая и понятная архитектура на старте:
- Frontend: Next.js App Router;
- Content: Supabase (раньше — локальные данные);
- Admin: простая панель управления контентом;
- Backend: минимальный, по мере необходимости.

Баланс между простотой, показуемым результатом, обучением архитектуре и постепенным ростом.

### Отдельный backend — решение (2026-07-24)

Пересмотрено «по-сеньорски». **Уточнение:** backend у нас уже есть — Supabase (BaaS: Postgres/Auth/Storage/RLS/Edge Functions) + серверный код Next.js (route handlers + серверные компоненты). Вопрос не «есть/нет backend», а «выносить ли часть в отдельный самостоятельный сервис».

**Решение: сейчас НЕ выносить, держать монолит (Next.js fullstack).** Причины: соло-разработка (скорость важнее всего), один язык/репозиторий/деплой, общие типы, нет второго потребителя API, нет проблемы масштаба. CRM/внутренние инструменты — это защищённые роуты `/admin`, а не повод для отдельного сервиса.

**Триггеры, при которых заводим отдельный сервис/воркер** (кандидаты: Supabase Edge Functions, очередь Inngest/QStash, маленький воркер на Hostinger VPS) — точечно, по конкретной нагрузке, не «backend вообще»:
1. Обработка файлов/картинок (сжатие тяжёлых оригиналов, генерация превью) — плохо ложится на serverless (таймауты).
2. Массовая рассылка (n8n + ESP — фактически уже внешний сервис).
3. Тяжёлые/частые крон-джобы, очереди, вебсокеты.

**Как остаться готовым без затрат сейчас:** модульный монолит — серверную логику держать в чистом слое-сервисе (`src/lib/*`, как `getProject`/`record_paid_order`), чтобы будущий вынос был переездом функции, а не переписыванием.

### Конвенция по API (2026-07-24)

Тип API: **свои эндпоинты — Next.js Route Handlers, RPC-стиль поверх HTTP+JSON** (URL = действие: `/api/checkout`, `/api/view`), не строгий REST. Плоский CRUD — **не пишем свои эндпоинты**, а идём через **Supabase SDK / авто-REST (PostgREST)**, который генерируется из схемы БД. GraphQL не используем. Секреты/обход RLS — только на сервере (`supabase-admin.ts`). Правило дублируется в `docs/RULES.md`.

## План развития — этапы 1-5

Этапы 2-5 намеренно кратко: детализировать каждый непосредственно перед стартом, а не заранее. Актуальный подробный статус — в `CLAUDE.md`.

| Этап | Статус | Коротко |
|---|---|---|
| 1. Базовый сайт-портфолио | 🟢 | лендинг, портфолио, about, contact, адаптив, деплой |
| 2. Контент и структура | 🟢 | подстраницы проектов, UI/UX, SEO и метаданные |
| 3. Сайт живёт на БД + админка | 🟡 | данные в Supabase — 🟢; своя `/admin` — частично |
| 4. Магазин / маркетплейс | 🟡 | A-E пройдены; остались креаторские хвосты и подписка |
| 5. Продвинутая инженерия | 🟡 | тесты и CI — 🟢; Docker, логирование, аналитика — 🔴 |

### 🟢 Этап 1. Базовый сайт-портфолио
Лендинг, раздел портфолио, «кто я», контакты, адаптивная вёрстка, деплой на Vercel. Готово, когда: сайт открывается по публичной ссылке, все страницы работают и адаптивны на мобильном, код в git. **Закрыт**: сайт на `soucampus.online`, адаптив пройден двумя проходами.

### 🟢 Этап 2. Улучшение контента и структуры
Отдельные страницы проектов, лучше UI/UX, SEO и метаданные. **Закрыт 2026-07-21**: OG/twitter-карточки, `sitemap.ts` из БД, `robots.ts`, canonical, JSON-LD.

### 🟡 Этап 3. Простая админка для контента
Мини-CMS в духе упрощённой Тильды под себя: добавление/редактирование проектов и секций без правки кода, контент в Supabase. Делается до магазина, чтобы контентом можно было управлять уже на этапе портфолио.

- 🟢 **Контент в Supabase** — весь сайт читает данные из Postgres (`projects`/`project_images`/`reviews`/`stats`), миграции в git.
- 🟢 **Первые реальные экраны админки** — `/admin` (сводка с графиком продаж), `/admin/moderation` (очередь карт), `/admin/products` (весь каталог), `/admin/applications` (заявки на креаторство), `/admin/announce` (рассылка уведомлений).
- 🔴 **Правка портфолио/отзывов/статов из своей админки** — сознательно осталось в Table Editor: требования собираются по ходу, а не угадываются заранее.

### 🟡 Этап 4. Магазин (подэтапы A-E)
Каталог, корзина, авторизация (Supabase Auth), оформление заказа, Stripe. Разбивка на подэтапы — в [`SHOP.md`](SHOP.md), там же статус каждого.

- 🟢 A/B/C — каталог, покупка одного товара, корзина и мульти-товарный чекаут.
- 🟢 D — Supabase Auth, профиль, My purchases, витрина-маркетплейс, оценки, мульти-креатор, загрузка карт с модерацией.
- 🟡 E — своя админка магазина: каталог и модерация есть, аналитика частично.
- 🔴 Подписка (Patreon-модель), версии карт и внешние ссылки у товара, поддомен `shop.soucampus.online`.

### 🟡 Этап 5. Продвинутая инженерия
Docker, CI/CD, тесты, логирование, безопасность, аналитика.

- 🟢 **CI/CD** — GitHub Actions (lint + тесты + build) на каждый пуш, автодеплой Vercel из `master`.
- 🟢 **Тесты** — 100 юнит-тестов в 14 файлах (Vitest), гоняются в CI.
- 🟡 **Безопасность** — RLS, триггеры состояний, подписанные ссылки, проверка сигнатур файлов есть; антивирус, квоты и аудит живыми людьми — нет.
- 🔴 **Docker, логирование, продвинутая аналитика** (PostHog) — не начато.

## Как подходить к обучению

**Что изучать параллельно:** Next.js и App Router, TypeScript basics, Tailwind basics, Git и GitHub, базовые принципы UI/UX, деплой через Vercel, переменные окружения и секреты, базовые принципы безопасности.

**Как работать с ИИ:** разбивать большие задачи на маленькие; задавать конкретные вопросы; не бояться переспросить; просить объяснение архитектуры и причин выбора решений; проверять результат, а не слепо копировать код.
