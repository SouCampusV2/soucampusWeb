# Магазин / маркетплейс построек — видение и план

Развёрнутое видение магазина (Этап 4+). `CLAUDE.md` держит короткий активный план и ссылается сюда; детали и последовательность — здесь. Спроектировано 2026-07-24 по описанию владельца.

## Что это такое

Не просто «магазин владельца», а **маркетплейс построек** в духе PlanetMinecraft: несколько креаторов публикуют постройки, покупатели их приобретают. На старте единственный креатор — владелец; система с самого начала проектируется под нескольких (как решение по подписке — заложить в схему, но не строить полный онбординг сразу).

## Изменённые решения (перекрывают прежний план)

- **Покупка только с аккаунтом.** Прежнее «гостевой чекаут остаётся» отменено — чекаут требует логина. Причина: почти всё (история покупок, доступ к файлам из профиля, просмотры по аккаунту, оценки, креаторы) завязано на наличие аккаунта.
- **Счётчик просмотров на портфолио убираем из публичного показа.** `ViewCount.tsx`/`SiteViews.tsx` на `/portfolio` снимаются — эту статистику владелец смотрит для себя (в админке/аналитике). На постройках магазина будет свой счётчик — **просмотры по аккаунту** (см. ниже), это другая механика.

## Витрина (главная магазина)

Ряды-категории (карусели), как на скриншоте-референсе:
- **Most popular** — по числу покупок/рейтингу.
- **Recently published** — по дате публикации.
- **Free** — постройки с ценой 0.
- **Top creators** — не постройки, а карточки креаторов (по продажам/рейтингу).

### Карточка постройки (структура — как референс, стиль/цвета — наши, см. `DESIGN.md`)

- превью-картинка (badge версии/лейбл в углу, напр. «1.12+», «Axiom available»);
- бейдж цены в углу картинки («$17.90» / «Free»);
- заголовок;
- имя креатора (акцентным цветом, кликабельно на профиль креатора);
- короткое описание в одну-две строки;
- звёзды рейтинга + число оценок;
- число покупок.

Карточка креатора («Top creators»): аватар, ник, суммарный рейтинг/фидбеки, число построек/продаж.

## Страница постройки

- галерея фото (креатор размещает фото где хочет — богатый макет, не фиксированная сетка);
- богатое описание (WYSIWYG-редактор при создании — не голый textarea, в духе Notion/Tiptap);
- информация о версиях Minecraft;
- кнопки-ссылки (превью-видео, Discord креатора, доп. материалы);
- цена + покупка (с логином);
- рейтинг, число покупок, просмотры по аккаунту;
- отзывы на постройку (оценка + текст).

## Профиль пользователя

**Сейчас (базовый):**
- имя, фамилия, отображаемый ник, email, пароль (если аккаунт по email; у OAuth-аккаунтов пароля нет — отсюда «если есть»);
- история покупок;
- доступ к файлам купленных построек (signed URL из приватного бакета `product-files` — переезжает из email-only в профиль).

**Ближайшее (запрошено 2026-07-24):**
- **аватарка** (загрузка в Storage, `avatar_url` в `profiles` уже заложен) + **редактирование профиля** (менять ник/имя/фамилию/аватар) — сейчас профиль только для чтения.

**На будущее:**
- **вход через Google (OAuth)** — второй способ входа рядом с email+password (решено 2026-07-24). Требует OAuth-приложение Google + redirect URLs; схема уже готова к этому («пароль если есть» — у OAuth-аккаунтов пароля нет).
- подключение Discord (OAuth-связь);
- кнопка «стать креатором» → аккаунт получает креаторский функционал;
- у креаторов — фидбеки (отзывы на самого креатора, отдельно от отзывов на постройки).

## Данные (эскиз, детально — в `STRUCTURE.md` при реализации)

Опорные сущности (проектировать под мультикреатора и подписку сразу):
- `profiles` — расширение `auth.users`: `first_name`, `last_name`, `display_name`, `is_creator` (bool, default false), `discord` (nullable, будущее).
- `products` — уже есть; добавить `creator_id → profiles`, `is_free`/цена, `published_at`, счётчики (кэш рейтинга/покупок) или считать через представления.
- `orders`/`order_items` — уже есть; связать с `profiles` (по email автоматически, как решено).
- `product_reviews` — оценка (1-5) + текст, `product_id`, `author_id`; уникальность «один отзыв на пару (product, author)».
- `creator_reviews` — фидбек на креатора: оценка + текст, `creator_id`, `author_id`.
- `product_views` — просмотр постройки по аккаунту: пара (product, viewer) + счётчик/дата (аналог нынешней схемы просмотров, но ключ — аккаунт, не cookie).

Рейтинг/число покупок/просмотров — производные: считать через SQL-представления/агрегаты, а не хранить руками (тот же принцип, что у нынешнего счётчика посетителей).

## Почта / письма (инфраструктура)

Две разные вещи, не путать:
- **Ящик для людей** (`support@soucampus.online` / `hello@…`) — чтобы принимать и отвечать. Домен на Hostinger → проще всего завести почтовый ящик там же (Hostinger Email / Titan), либо Zoho Mail (бесплатный тариф) / Google Workspace (платно).
- **Транзакционные письма из приложения** (ссылка на скачивание после покупки, подтверждение заказа, письма Supabase Auth о подтверждении email) — это НЕ обычный ящик, а email-API. Рекомендация: **Resend** (дружелюбен к Next.js, щедрый бесплатный тариф). Требует верификации домена — добавить DKIM/SPF/DMARC записи в DNS на Hostinger. From-адрес вида `orders@` / `noreply@`.
- **Чеки об оплате** отдаёт сам **Stripe** (включается в дашборде) — отдельно их слать не нужно.
- Порядок: сам Supabase Auth уже шлёт письмо-подтверждение регистрации (через свой SMTP по умолчанию — для прода позже подключить свой SMTP/Resend, чтобы письма шли с нашего домена и не попадали в спам).

## Разделение ресурсов портфолио ↔ магазин (2026-07-24)

Инстинкт владельца: магазинная логика в навбаре (cart-контекст, иконки) не должна грузиться на портфолио. Верно по принципу, но **не приоритет сейчас** — навбар это пара КБ JS, реальная тяжесть портфолио — картинки 5-14 МБ (см. `CLAUDE.md` open task «Оптимизация картинок»). План: (1) сначала картинки; (2) разделение навбара на `PortfolioNavbar`/`ShopNavbar` (или `next/dynamic` на магазинную ветку) сделать вместе с витриной-маркетплейсом; (3) финал — магазин на отдельном поддомене `shop.soucampus.online` = полностью разные бандлы. Не микрооптимизировать навбар отдельно.

**Переход на поддомен `shop.soucampus.online` — ОБЯЗАТЕЛЬНЫЙ, не опциональный (решено 2026-07-24).** У магазина будет СВОЙ отдельный навбар (`ShopNavbar`), а не режим общего навбара, как сейчас. Текущий «режим магазина» внутри общего `Navbar.tsx` — временное решение на период разработки в `(site)/shop`; при выносе на поддомен навбар разделяется физически.

## Порядок реализации (подэтапы)

Зависимости диктуют порядок — почти всё висит на аккаунтах, поэтому auth первым.

1. **Auth (фундамент).** Supabase Auth: регистрация/вход (email+password для старта; **Google OAuth — следующим способом входа**, потом Discord), сессия в Next.js (proxy.ts + серверные хелперы), защищённые маршруты. Гейт на чекаут (покупка требует логина).
2. **Профиль (базовый).** Страница профиля: поля (имя/фамилия/ник/email), смена пароля. Таблица `profiles` + триггер на создание при регистрации.
3. **Покупки в профиле.** История заказов + доступ к файлам из профиля (перенос из email). Привязка старых гостевых заказов по email.
4. **Витрина-маркетплейс.** Ряды-категории (Most popular / Recently / Free / Top creators), карточки в нашем стиле.
5. **Оценки и просмотры построек.** `product_reviews`, `product_views` (по аккаунту), отображение рейтинга/покупок/просмотров на карточке и странице.
6. **Убрать счётчики просмотров с портфолио** (публичный показ) — независимо, можно раньше.
7. ~~**Креаторский UI загрузки постройки**~~ — **СДЕЛАНО 2026-07-30.** `/creator/upload`: WYSIWYG-описание на Tiptap с картинками и таблицами внутри текста, галерея с перетаскиванием и выбором обложки, категория, цена, загрузка файла в `product-files`. Плюс то, чего в плане не было, но без чего оно не работает: **очередь модерации** `/admin/moderation` (заявка не попадает на витрину без одобрения), отказ чек-листом с проверкой при повторной отправке, правка своих карт `/resources/[slug]/edit`. Версий и внешних ссылок пока НЕТ — они остались из этого пункта неcделанными.
8. **Креаторы (полноценно, будущее).** «Стать креатором», профиль креатора, фидбеки на креатора, «Top creators».
9. **Подписка (Patreon), будущее.** См. `IDEAS.md`.
