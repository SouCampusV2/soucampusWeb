Название сайта: **SouCampus builds**. Портфолио + магазин Minecraft-карт + обучение веб-разработке.

Этот файл держит только **активный план** и **текущий статус**. Всё стабильное вынесено в `docs/` — открывать по необходимости:

- [`docs/DESIGN.md`](docs/DESIGN.md) — дизайн-система: цвета, типографика, переиспользуемые компоненты (`Button`, `ArrowCircle`), вёрстка, анимация перехода. Сверяться перед любой правкой стиля/вёрстки.
- [`docs/STRUCTURE.md`](docs/STRUCTURE.md) — схема БД Supabase (`projects`/`project_images`/`reviews`/`stats`), RLS, миграция «массив → БД», структура сайта (навигация/страницы/магазин).
- [`docs/ROADMAP.md`](docs/ROADMAP.md) — долгосрочное видение, стек и почему такой, крупные этапы 1-5, как учиться.
- [`docs/SHOP.md`](docs/SHOP.md) — **видение магазина-маркетплейса** (креаторы, витрина-категории, профиль, оценки, порядок подэтапов). Главный ориентир по Этапу 4+.
- [`docs/IDEAS.md`](docs/IDEAS.md) — бэклог идей не из текущего спринта (Patreon-подписка, PostHog, кастомная админка, graphify, Discord-бот).
- [`docs/CHANGELOG.md`](docs/CHANGELOG.md) — датированный дневник, что сделано и почему. Открывать, чтобы вспомнить, почему что-то устроено именно так.

## Задачи на сессию (с чего начинать)

Текущая фаза (**решение владельца 2026-07-27**): **быструю разработку новых фич останавливаем — переходим в доводку.** Магазин-маркетплейс доведён до рабочего мульти-креатора и лежит в проде; дальше вместо новых подэтапов занимаемся: (1) **производительностью/оптимизацией страниц**, (2) **анимацией**, (3) **логикой и контентом**, (4) **внешним видом — последним**, по замечаниям владельца (он сам подмечает и приносит правки). Владелец параллельно строит в Minecraft, поэтому крупные правки лучше согласовывать по ветке.

**Магазин НЕ индексируем, пока нет реального товара** (решение 2026-07-27, при разборе Google Search Console): `/shop` остаётся в `noindex`. Снять — когда появятся настоящие карты с файлами вместо демо-сида. GSC при этом уже работает: 5 страниц в индексе, 26 «обнаружена, не проиндексирована» (нормальная очередь у молодого домена), 2 редиректа, 1 расхождение по каноникалу.

### Телеграм-отчёт — разобрано и починено (2026-07-30)

**Причина:** в облачном окружении routines `api.telegram.org` **закрыт сетевой политикой** — прокси отвечает `403 Forbidden` на CONNECT. То есть еженедельный отчёт НИКОГДА не доходил: файл исправно собирался и коммитился в `master`, а отправка молча падала (в промпте было «упала — упомяни в итоге, но не роняй routine», а итог никто не читал). Ручная отправка тем же ботом работает — проверено, три отчёта дошли.

**Как теперь:** доставку делает **GitHub Actions** (`.github/workflows/report-to-telegram.yml`) — раннеры в интернет ходят свободно. Routine кладёт отчёт в `reports/`, коммит в `master` запускает workflow, тот шлёт файл в Telegram. Из промпта routine шаг отправки убран, вместо него объяснение, почему его там нет.

**⚠️ Нужно от владельца, иначе не заработает:** добавить два секрета в GitHub → Settings → Secrets and variables → Actions:
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_CHAT_ID` (`1092351768`)

Проверить, не дожидаясь понедельника: вкладка Actions → «Send weekly report to Telegram» → Run workflow.

**⚠️ Токен стоит перевыпустить** у @BotFather: он лежал открытым текстом в промпте routine (и в переписке). После перевыпуска новый класть только в секреты GitHub.

Диагностическая routine «Telegram heartbeat» **выключена** — своё дело сделала. Удалить совсем: https://claude.ai/code/routines

**Заодно:** отчёт покрывает ровно 7 дней (`git log --since='7 days ago'` в промпте). Владелец спрашивал про две недели — правка одной строки.

### Ближайший приоритет (решено 2026-07-30, порядок осознанный)

Сначала безопасность, потом удобство. **Первые три — до того, как на сайт придут посторонние креаторы и включатся живые платежи.**

1. **Сканирование загружаемых файлов на вредоносность.** Сигнатуры уже проверяются (`src/lib/upload-limits.ts`), но настоящего антивируса нет, а файлы раздаются покупателям под брендом сайта. Варианты (внешний API против своего микросервиса со ClamAV) — в `docs/IDEAS.md` → «Проверка загружаемых файлов». Туда же: распаковка zip и проверка содержимого, защита от zip-бомб.
2. **Уборка мусора в Storage (найдено 2026-07-30 при проверке базы).** При замене файла карты или картинок старые объекты из бакетов НЕ удаляются — остаются навсегда. Проверено на живых данных: одна карта после двух правок оставила два лишних zip'а по ~3.5 МБ. Растёт линейно с числом правок, в платном хранилище. Чинить служебным ключом через свой route handler (у `product-files` политики DELETE нет и быть не должно — иначе креатор удалит чужой файл), удалять старый объект ТОЛЬКО после успешной записи нового `file_path`. Сюда же — сироты от картинок в описании, если форму не отправили.
3. **Квоты на загрузку.** Лимит размера есть, лимита количества нет — любой может забить платное хранилище. Детали — `docs/IDEAS.md` → «Квоты на загрузку».
4. **Аудит безопасности живыми людьми** перед включением реальных платежей — денежный путь (Stripe + вебхук), раздача файлов, юридическая сторона площадки. Обсуждено 2026-07-30.
5. **`/admin/products`** — бан/архив/разбан любых карт + поиск по названию и автору, журнал действий (`moderation_log`). Проработано 2026-07-30: статусы `suspended` (скрыл модератор, креатор не вернёт) и `archived` (убрал сам автор). Три подводных камня, зафиксированных при проработке: покупатели ОБЯЗАНЫ сохранить доступ к скачиванию забаненной карты (сейчас работает, т.к. `getPurchasesForUser` читает служебным ключом — закрепить тестом); корзина молча выбрасывает снятую позицию, нужна причина в UI; ISR держит страницу до 60с, для срочного бана нужен `revalidatePath`.
6. **Messages / Notifications** — раздел не реализован, заглушки в навбаре стоят. Нужен под доставку креатору причин отказа/бана + шаблоны сообщений (`docs/IDEAS.md`).
7. **Hostinger SMTP → Supabase**, затем письма модерации со ссылкой в админку (`docs/IDEAS.md`). Без SMTP сброс пароля упирается в лимиты встроенной почты Supabase.
8. **Google-вход (OAuth).** Обсуждено 2026-07-30, вывод: делать НЕ раньше, чем появятся посторонние пользователи, и обязательно продумать выбор ника при первом входе (Google ника не даёт) + слияние аккаунтов на один email.
9. **Версии карт и внешние ссылки у товара.** Входили в подэтап 7 `docs/SHOP.md` и НЕ построены. Версии Minecraft (1.8–1.21) нужны **отдельным полем**, а не текстом в описании — иначе по ним нельзя фильтровать и они выглядят по-разному у каждого креатора. Ссылки — кнопки на превью-видео, Discord автора, доп. материалы.
10. **Ограничить `img src` в описании** нашим бакетом Storage — сейчас креатор может вставить картинку с чужого сервера и собирать IP посетителей.

### Мелькание состояния до гидратации — разобрано и пофикшено (2026-07-25)
**Вывод исследования «можно ли определять состояние ДО загрузки»:** нельзя без отказа от статики. `/shop/[slug]` и портфолио собираются заранее (`generateStaticParams` / ISR) — один HTML на всех, сервер физически не может знать ни корзину (она в `localStorage`), ни кто залогинен. Вариант «cookie + читать на сервере» помог бы только если сделать страницы **динамическими** (рендер на каждый запрос) — а это жертва производительностью, которую проект бережёт. Поэтому пошли путём (в) из плана — убрать мелькание **неверного** состояния, не жертвуя статикой:
- **Навбар (аватар/ник):** `useUser` переведён с `getUser()` (валидация по сети — отсюда задержка) на `getSession()` (мгновенно из хранилища; для отображения ОК, авторизация всё равно на сервере). Пока состояние неизвестно — нейтральная `Skeleton`-заглушка вместо иконки «войти», размер совпадает → без сдвига.
- **Кнопка на товаре:** новый хук `src/lib/useHydrated.ts` (через `useSyncExternalStore`, false на SSR+гидратации → true после) делает `inCart` детерминированным; `min-h` резервирует строку под «View cart», чтобы её появление не дёргало вёрстку. Для большинства (товара нет в корзине) «Add to cart» — сразу корректный первый кадр.
- **Полное устранение** оставшегося «pop-in» (аватар/ник и in-cart-кнопка появляются после гидратации) требует динамического рендера — сознательно НЕ делаем ради статики. Если когда-нибудь захотим ноль pop-in — вариант: вынести магазин на динамический рендер с cookie-корзиной, оставив портфолио статикой.

### Градиент (свечение) — приведён к одному виду (2026-07-27)
**Почему он «постоянно ломался»:** свечение существовало в **семи копиях**, и чинилась каждый раз одна. Разъехались: пять высот (772/676/640/512px), два отступа сверху (`-top-32`/`-top-40`), два рецепта градиента (дефолтный `circle` с farthest-corner против явного `ellipse 60% 100%`) и два способа задать ширину (`w-full`/`w-screen`). Плюс `PageGlow` держался на неписаном контракте с родителем.
- **Теперь:** вся геометрия — константы в `src/components/PageGlow.tsx` (`HEIGHT` 48rem, `OFFSET_TOP` −40, `WIDTH` `w-screen max-w-[90rem]`), наружу торчит **только цвет**; проп `className` убран намеренно — им и разъезжались высоты. На компонент переведены `Hero`, `PortfolioHero`, `/contact`, `/terms` (копипастов в классах не осталось), плюс уже бывшие на нём `/shop`, `/creator`, `/purchases`, `/settings`, `/login`, `/signup` (и новые `/resources`, `/forgot-password`, `/reset-password`).
- **Правило (важное, не забыть):** `overflow-x-clip` вешается на **полноширинный** родитель, а `max-w-*` живёт на обёртке контента **внутри** него. На одном элементе контейнер отрезает то самое свечение, которое должен вмещать — это была четвёртая, последняя причина срезов.
- Высота эталонная — по hero лендинга; на страницах, где было 640px (и 512px на `/creator`), свечение стало заметно больше. Цвета не менялись. Не понравится — это одна константа.
- **Выпадашка профиля — выровнена (2026-07-29).** Скриншот с разметкой (красные линии по бокам + синяя по высоте) дошёл в следующей сессии: карточка меню (`Navbar.tsx`) держалась на фиксированной `w-48`, из-за чего при коротких/длинных никнеймах уезжала мимо профиля. Убрал фиксированную ширину — обёртка меню теперь `w-full` внутри контейнера, который сам по себе размером с триггер (аватар+ник), поэтому левый/правый край выпадашки всегда совпадают с самим профилем; `top` без изменений (`calc(100%+8px)`, тот же зазор, что уже был).

## Текущее состояние сайта

Компактный снимок «что сейчас есть» — не история (за ней `docs/CHANGELOG.md`).

- **Стек:** Next.js 16 (App Router) + TypeScript + Tailwind v4, `framer-motion` (`motion/react`), `@phosphor-icons/react`.
- **Страницы:** `/` (лендинг), `/portfolio` + `/portfolio/[slug]`, `/reviews/[slug]` (заглушка, доработать), `/about`, `/contact`, `/terms` (частично реальная), `/shop` + `/shop/[slug]`, `/cart`, `/support`.
  - **Аккаунт (перестроен 2026-07-30):** `/settings` (профиль + смена пароля), `/purchases` (только покупки), `/resources` (свои карты со статусами) + `/resources/[slug]/edit`. Старые `/profile` и `/profile/edit` оставлены редиректами — на них ведут письма Stripe и закладки.
  - **Вход:** `/login`, `/signup`, `/forgot-password`, `/reset-password`, `/auth/callback`.
  - **Креатор:** `/creator/[username]` (публичный профиль), `/creator/upload` + `/creator/upload/submitted`.
  - **Админка:** `/admin/moderation` — ВНЕ группы `(site)`, без навбара и футера, гейт в трёх местах (proxy, layout, сам обработчик API). Постороннему отдаёт 404, а не 403.
- **Компоненты лендинга** (в порядке на главной): `Hero`, `Stats`, `RecentProjects`, `CountriesMarquee`, `ClientReviews`, `HowItWorks`, `AuthorCta`, `PricingSection`, `ContactFooter`. Общие: `Navbar`, `PageTransition` (см. `docs/DESIGN.md`), `Skeleton`. `Navbar`, `PageTransition`, `PricingSection`, `ContactFooter` подключены в `src/app/(site)/layout.tsx`, не в отдельных `page.tsx`.
- **Роутинг:** публичные страницы в группе `src/app/(site)/` — скобки: сегмент не попадает в URL, нужен только для общего layout. Корневой `src/app/layout.tsx` держит только общее для всех: `<html>/<body>`, шрифт, `ThemeProvider`, Vercel Analytics. Будущая админка — `src/app/admin/`, вне `(site)`, не наследует навбар/тарифы/футер.
- **Деплой:** прод `https://soucampus.online` (свой домен, DNS через Hostinger hPanel), автодеплой через Vercel GitHub App — пуш в `master` пересобирает прод. CI (GitHub Actions: lint+build) — на каждый пуш/PR. Аналитика — Vercel Analytics.
- **Портфолио:** `src/lib/projects.ts` — 16 работ с настоящими фото (`public/portfolio/`), все данные реальные. `/portfolio` — hero-карусель `PortfolioHero.tsx` (первые 5, hover/tap-раскрытие на десктопе, свайп на мобильном) + bento-сетка «More projects». Клик ведёт на `/portfolio/[slug]` без анимации перехода (`PageTransition` — только на ссылках навбара).
- **Отзывы:** `src/lib/reviews.ts` — 7 реальных отзывов (`name/role/flag/text/accent/slug`), «table-shaped» паттерн как у `projects.ts`. Каждый кликабелен («Read story») на `/reviews/[slug]` — сейчас заглушка, доработать. Тот же подход в `Stats.tsx`/`CountriesMarquee.tsx`.
- **Счётчик просмотров (2026-07-20):** считается весь сайт — трекер в `(site)/layout.tsx`, адрес через `usePathname()`. Показывается на `/portfolio`: у каждой работы своё число (`ViewCount.tsx`) + общий счётчик уникальных посетителей сайта с фильтром периодов (`SiteViews.tsx` — All time/Month/Week/Today, все четыре числа одним запросом). Один человек = единица, сколько бы страниц ни обошёл.
  - **Схема:** строка на тройку (страница, посетитель, день) — иначе периоды невычислимы. «За всё время» = `count(distinct visitor_id)`.
  - **Почему через браузер:** страницы статические (`revalidate = 60`), серверный код раз в минуту, не на гостя. Сигнал шлёт браузер в `/api/view`.
  - **Доступ:** `page_views` закрыта для анонима без единой политики. Пишет/читает только сервер под служебным ключом (`supabase-admin.ts`, `SUPABASE_SERVICE_ROLE_KEY` без `NEXT_PUBLIC_` — не попадает в браузерный бандл).
  - **Защита от накрутки:** cookie подписана HMAC (`visitor-cookie.ts`); не более 60 РАЗНЫХ посетителей с адреса в час (считаются посетители, не строки); хэш только от IP без User-Agent; сам IP не хранится, только хэш с солью (`VIEW_HASH_SALT`).
  - **Проверка:** юнит-тесты на подпись/белый список + `npm run check:views` (ручной прогон против живого обработчика, чистит за собой по `ip_hash`). В CI не гоняется намеренно.
  - **Решено убрать из публичного показа (2026-07-24):** `ViewCount.tsx`/`SiteViews.tsx` снять с `/portfolio` — статистика уходит владельцу в админку/аналитику. На постройках магазина будет свой счётчик просмотров по аккаунту (см. `docs/SHOP.md`). Серверную инфраструктуру счётчика (`/api/view`, `page_views`) пока не трогать — решить при снятии, что переиспользуется.
- **Тарифы:** `PricingSection` — UI и цены финальные. Идея подписки (Patreon) — `docs/IDEAS.md`.
