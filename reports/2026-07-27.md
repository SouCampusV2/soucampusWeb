## Термины и технологии

| Термин | Объяснение |
|---|---|
| Row-Level Security (RLS) | Механизм PostgreSQL/Supabase, ограничивающий, какие строки таблицы видит и может менять конкретный пользователь — политики пишутся на уровне БД, а не в коде приложения. На этой неделе именно RLS была причиной, почему оценки товаров не сохранялись: проверка "покупал ли этот пользователь товар" сама упиралась в RLS других таблиц. |
| `SECURITY DEFINER` функция | Функция в PostgreSQL, которая выполняется с правами того, кто её создал (обычно с более широким доступом), а не с правами вызывающего пользователя — позволяет безопасно "заглянуть" в данные, закрытые RLS, но только через строго определённую логику внутри функции. Так фикс `has_purchased()` смог проверить покупку, не открывая всей таблицы заказов. |
| Webhook и проверка подписи (Stripe) | Webhook — это когда внешний сервис (Stripe) сам присылает уведомление на наш сервер о событии (оплата прошла). Проверка подписи — сверка криптографической подписи запроса с секретным ключом, чтобы убедиться, что уведомление действительно от Stripe, а не подделано кем-то ещё. |
| Hydration (гидратация) и "pre-hydration flash" | Гидратация — момент, когда React "оживляет" уже отрисованный сервером HTML, добавляя к нему интерактивность на клиенте. До этого момента страница на экране статична, и если какое-то состояние (например, "товар уже в корзине?") известно только в браузере, при первом кадре оно может мигнуть неверным значением, а потом резко поменяться — это и есть "pre-hydration flash", пофикшенный на этой неделе. |
| `useSyncExternalStore` | Хук React, созданный специально для безопасной (без гидратационных нестыковок) подписки компонента на внешнее хранилище — вроде `localStorage` или самодельного стора корзины. Использован в новом `useHydrated.ts`, чтобы кнопка "Add to cart" знала первый корректный кадр. |
| RPC vs REST | REST у Supabase — это автоматически сгенерированный (PostgREST) доступ к таблицам через SDK, где запрос описывает "что взять", а не "что сделать". RPC (Remote Procedure Call) — вызов конкретной именованной функции на сервере БД (например, `record_paid_order()`, `has_purchased()`), когда нужна не выборка данных, а атомарное действие с логикой внутри одной транзакции. |
| Атомарность транзакции | Свойство операции с БД "всё или ничего" — либо все шаги (списать заказ, создать позиции заказа, привязать к пользователю) выполняются успешно вместе, либо откатываются все разом. Важно для оплаты — нельзя создать заказ без позиций или наоборот при сбое посередине. |
| Suspense-граница (React) | Способ сказать React "пока этот кусок компонента не готов (грузит данные/читает параметры URL) — покажи заглушку вместо ошибки". Использован в `ShopCatalog`, потому что чтение `?category=`/`?q=` из URL требует такой границы в Next.js. |
| Миграция (SQL) и порядок preview → прод | Файл с SQL-изменением схемы БД (новая таблица, функция, политика). Правило проекта — каждую миграцию сначала прогонять на тестовой базе (preview), проверять, что работает, и только потом на настоящей (прод) — на этой неделе так и было сделано с миграциями оценок и RLS-фикса. |
| Скоуп токена CI (`contents: read`) | В GitHub Actions у `GITHUB_TOKEN` по умолчанию довольно широкие права; явное ограничение до `contents: read` в конфиге workflow означает "этому пайплайну разрешено только читать код репозитория", ничего не менять и не публиковать — снижает ущерб, если в пайплайн проникнет вредоносный код. |
| AVIF/WebP форматы изображений | Современные форматы сжатия картинок, заметно легче классических JPEG/PNG при том же визуальном качестве. Next.js (`next/image`) сам отдаёт браузеру подходящий формат из списка разрешённых в `next.config.ts` — на этой неделе список включён, а сами исходники дополнительно сжаты на диске. |
| RLS-совместимая проверка через email | Паттерн, когда гостевой заказ без привязки к аккаунту (`user_id = null`) всё равно можно посчитать "своим" для вошедшего пользователя, если email заказа совпадает с email аккаунта (`auth.email()`) — временное решение до полноценной привязки гостевых заказов по email при регистрации (см. план Этапа 4). |
