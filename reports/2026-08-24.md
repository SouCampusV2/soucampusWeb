## ⚠️ Главное, на что стоит посмотреть в первую очередь

**Прошлая находка закрыта в тот же день, как отчёт был прочитан.** Отчёт от 2026-08-17 указал, что `ModerationActions.tsx` не перешёл на `DANGER_COLORS` — кнопки «Reject»/подтверждение выглядели ярче, чем «Delete» в каталоге, хотя обе делают одно и то же (опасное действие). Хороший знак: находки отчёта реально доходят до кода.

**Новая находка, требующая решения владельца: палитра цвета ника нарушает правило «красный — только для трёх служебных случаев».** `src/lib/name-colors.ts:33-40` (фича этой недели, `NameColorPicker.tsx`) предлагает восемь цветов на выбор, и среди них — `Red` (`#e11d48`), `Green` (`#15803d`) и `Violet` (`#8b5cf6`). `docs/DESIGN.md` разрешает только три акцента (orange/blue/lime) плюс красный исключительно для ошибок/разрушения/отказа — «вне этих трёх случаев красного быть не должно, ни в декоре, ни в акцентах». Здесь red — просто один из декоративных вариантов цвета ника, прямое противоречие. Расчёт контраста в файле честный (WCAG 3.0 для крупного текста, взяты все восемь), вопрос не в контрасте, а в самом наборе цветов. Фича совсем новая, `DESIGN.md` её не фиксирует вообще — нужно явное решение: либо узаконить отдельную палитру ника как исключение (по образцу того, как red стал служебным цветом 2026-07-28), либо сузить список до вариаций трёх акцентов. Предложение — вынести общую функцию вида `async function readErrorMessage(response: Response, fallback: string): Promise<string>` в `src/lib/rate-limit.ts` (или отдельный `src/lib/api-error.ts`, раз не все вызовы связаны именно с лимитами — тот же 404/500-текст проходит по той же логике) и переиспользовать её во всех перечисленных компонентах вместо копий `data?.message ?? data?.error ?? "…"`. Не блокирующая правка, но ровно тот случай «повторяющаяся логика форматирования, скопированная в нескольких файлах», который чек-лист просит явно отметить.

✅ Формула видимости `state = 'live' AND creator_active` — сверена во всех местах, которые её повторяют (`src/lib/products.ts:409-410,499-500`, `src/lib/catalog.ts:74`, `src/lib/moderation.ts:172`, `src/lib/analytics.ts:208`) — везде дословно совпадает, расхождений не найдено.

## Термины и технологии

| Термин | Объяснение |
|---|---|
| Вычисляемая (generated) колонка | Колонка, значение которой Postgres считает сам по формуле от других колонок той же строки и хранит физически (`generated always as (...) stored`) — в отличие от обычной, её нельзя записать напрямую. `profiles.username_lower` (`20260821150000_one_name.sql`) считается как `lower(username)`: уникальность и поиск профиля по адресу регистронезависимы, а PostgREST умеет фильтровать только по настоящим колонкам — выражение `lower(username) = $1` из клиента не выразить, а обычный `ilike` не использует функциональный индекс. |
| Rewrite vs Redirect (Next.js) | Redirect отправляет браузеру новый адрес и меняет то, что видно в адресной строке; rewrite подменяет адрес незаметно для посетителя — URL остаётся прежним, а Next отдаёт содержимое другой страницы. Профиль `/@<username>` (`next.config.ts`) устроен именно так: реальный файл лежит по `/u/[username]/page.tsx` (папка не может начинаться с `@` — это зарезервировано под параллельные маршруты App Router), а красивый адрес — rewrite поверх него. Отсюда следствие: `revalidatePath` должен целиться в `/u/<имя>`, потому что для Next существует только этот путь. |
| React `cache()` | Функция, которая оборачивает асинхронный вызов (например, поход в базу) так, что повторный вызов с теми же аргументами в пределах ОДНОГО рендера возвращает уже готовый результат, а не делает второй запрос. Next вызывает `generateMetadata` и сам компонент страницы отдельно, и оба звали `getProduct(slug)`, — обёртка `const getProductOnce = cache(getProduct)` (`marketplace/[slug]/page.tsx`) убрала лишний запрос без изменения кода вокруг. |
| Скользящее окно (rolling window) vs счётчик со сбросом | Способ считать «сколько действий за последний час»: скользящее окно смотрит на реальные метки времени прошлых действий, счётчик со сбросом обнуляет число в начале часа по календарю. Второй вариант даёт дыру на стыке: можно исчерпать лимит в 10:59 и получить ещё один полный лимит в 11:01. `ops.rate_events` (таблица-журнал) и `consume_rate_limit()` (`20260823120000_api_rate_limits.sql`) считают именно скользящее окно — строка живёт, пока не истечёт её собственный час. |
| `GRANT`/`REVOKE EXECUTE` и роль `PUBLIC` | В PostgreSQL право вызывать новую функцию по умолчанию получает служебная роль `PUBLIC` — то есть буквально кто угодно, если явно не отозвать. `consume_rate_limit()` лежит в схеме `public` (потому что таблица `ops.rate_events` не выставлена через PostgREST, а функция обязана быть там, откуда её можно позвать), и без `revoke execute on function ... from public, anon, authenticated` вызвать её из консоли браузера мог бы любой посетитель сайта. |
| `pg_advisory_xact_lock` | Именованная блокировка в PostgreSQL, которую можно взять на пару произвольных чисел (не строку таблицы) на время транзакции — она сама снимается по завершении. `consume_rate_limit()` берёт такую блокировку на пару (bucket, actor), чтобы два одновременных запроса одного человека не увидели одно и то же «использовано 9 из 10» и не прошли оба — без замка получилось бы 11 вместо 10. |
| `text[]` + GIN-индекс vs таблица связей | Классический учебный ответ на «у товара много значений одного поля» — отдельная таблица со внешним ключом (`product_versions`). Для характеристик карты (`mc_versions`, `game_modes`, `themes` — `20260821130000_product_specs.sql`) выбран массив строк с GIN-индексом: у значения нет собственных свойств, число элементов не растёт бесконечно, а нужны только «показать» и «отфильтровать» — то, что GIN-индекс по массиву делает без join'ов. |
| Идемпотентность и повторные вебхуки | Вебхук — это когда внешний сервис (Stripe) сам стучится к нам с уведомлением о событии; при неудачном ответе Stripe повторяет доставку позже. Поэтому `/api/stripe/webhook` сознательно не подчиняется общим лимитам частоты (`docs/STRUCTURE.md` § 5.3) — отказ там означал бы «деньги списаны, а заказ не записан», и повторная попытка — это не злоупотребление, а единственный способ Stripe убедиться, что уведомление дошло. |
| Контраст WCAG и пороги 3.0 / 4.5 | Стандарт доступности требует разного минимального контраста текста к фону в зависимости от размера: 4.5:1 для обычного текста, 3.0:1 — для крупного/жирного (эффективно бо́льшая площадь буквы легче читается при меньшем контрасте). Восемь цветов в `NameColorPicker` посчитаны именно под порог 3.0, потому что ник на профиле — крупный жирный текст; те же цвета под подписью где-нибудь в мелком тексте порог 4.5 уже не возьмут, и это ограничение явно записано в коде. |
| Оптимистичное обновление (optimistic UI) | Приём, при котором интерфейс меняется сразу по клику, ещё до ответа сервера, — а если запрос всё же вернёт ошибку, изменение откатывается обратно. `ReactionButton.tsx` увеличивает счётчик реакции в тот же кадр, что и нажатие, не дожидаясь записи в базу: без этого по медленной реакции сервера человек решил бы, что клик не сработал, и нажал повторно. |
| Двухфазный рендер и «намеренно неверный» первый кадр | Приём для страниц, которые заранее собираются в статику: сервер не знает часовой пояс читателя, поэтому первый показанный кадр рисуется в UTC — том же виде, что был на сервере при сборке, — а после гидратации React тихо подменяет его на местное время. Показать сразу локальное время значило бы, что HTML на экране разойдётся с тем, что React ожидает увидеть при оживлении страницы, — а это приводит к ошибке гидратации (#418), на которой уже терялось полдня на странице уведомлений. `LocalTime.tsx` использует именно эту схему: секунду висит «неправильная» UTC-дата, потом бесшумно становится верной. |
