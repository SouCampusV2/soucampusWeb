### 2. Консистентность компонентов-паттернов

- 🟡 **Запрос к вебхуку Discord написан дважды независимо, в двух файлах
  одного и того же вечера.** `discord-announce.ts:69-82`

  `discord-showcase.ts:255-261` (используется `publishPost`/`updatePost`/

  операция «сходить в вебхук Discord», написанная заново, потому что
  `discord-announce.ts` и `discord-showcase.ts` создавались в разные
  часы того же дня (26–27.10) и не знали друг про друга. Предложение —
  общий модуль `discord-webhook.ts` с единственной функцией

  Цена невынесения — не баг сегодня, а то, что следующая правка формата
  ошибки («Discord answered …») почти наверняка попадёт в один файл и
  забудет про второй.

## Термины и технологии

| Термин | Объяснение |
|---|---|
| Вебхук Discord (`webhook`) | Готовый URL, который Discord выдаёт для канала: POST на него с JSON-телом публикует сообщение от имени «приложения», без токена бота и без прав на сервере. Этот период завёл **два** независимых клиента к одному и тому же механизму (`discord-announce.ts` для объявлений, `discord-showcase.ts` для постов-витрины) — находка «Проверка структуры» → п. 2 именно про то, что один и тот же низкоуровневый вызов написан дважды. |
| `fetchFn: typeof fetch = fetch` (внедрение зависимости для тестов) | Приём, когда функция принимает `fetch` параметром с дефолтным значением «настоящий fetch», а в тестах туда подставляется поддельная функция, которая ничего не шлёт по сети, а возвращает заготовленный ответ. Так `discord-showcase.test.ts`/`discord-announce.test.ts` проверяют формат запроса и разбор ответа Discord без единого реального HTTP-запроса. |
| `aria-pressed` / `role="tablist"` / `role="dialog"` | Атрибуты доступности (ARIA), которые говорят программам чтения с экрана, что перед ними не обычный текст, а интерактивный элемент с состоянием: `aria-pressed` — «эта кнопка нажата/активна» (использован в `ProfileLinksDialog`), `role="tablist"`/`aria-selected` — «это вкладки, вот какая выбрана» (`ProfileTabs.tsx`), `role="dialog" aria-modal="true"` — «это модальное окно, остальная страница сейчас не активна». Без них те же элементы визуально работают одинаково, но незрячий посетитель с программой чтения экрана не поймёт, что происходит. |
| `Number.isInteger(stars * 2)` — проверка шага в половину | Способ проверить, что число кратно 0.5, без отдельной библики для дробей: `stars * 2` для 3.5 даёт 7 (целое, подходит), а для 3.3 — 6.6 (не целое, не подходит). Используется в `isValidStars` (`map-review-shape.ts`) — отзыв на карту принимает только целые и половинные звёзды. |
| `confirm()`/`alert()` и «не спрашивать больше» | Встроенные диалоги браузера. У человека есть галочка «больше не показывать диалоги для этой страницы» (Chrome показывает её после пары `confirm()` подряд); после неё вызов **молча** возвращает `false`, без ошибки и без следа — кнопка, завязанная на такое подтверждение, выглядит сломанной без единой подсказки почему. Ровно для обхода этого в проекте есть свой `ConfirmDialog.tsx` — находка этого отчёта (`window.confirm` в трёх файлах) обходит именно эту защиту, уже дважды выученную ценой сломанных кнопок (23.08, 25.08) и один раз названную прошлым отчётом. |
| `git revert` отката, затем обычный мёрж | Когда ветку `dev` однажды уже вливали в `master` и откатывали `git revert`-ом (история прошлого отчёта, 24.10), повторная попытка не может быть обычным мёржем: git считает содержимое отката уже «влитым» и не принесёт изменения снова. Правильный порядок — сперва `git revert` самого отката (это возвращает код на место), потом обычный `git merge dev`. Применено 27.10 ровно в этом порядке, как и предписывалось в прошлом отчёте. |
| `security definer` / чистые функции с `fetchFn` vs RPC | Не из этого периода напрямую, но рядом: квоты (`creator-quotas.ts`) — чистые функции над числами (сколько уже загружено, сколько можно), без обращений к базе внутри самой функции. Проверка «не превышена ли квота» делает отдельный код, который спрашивает базу и передаёт готовые числа в эти функции — та же граница, что у `checkMapSubmission`: проверка отдельно от похода за данными, чтобы тестировать проверку не поднимая базу. |
| `dynamic = "force-dynamic"` на личных страницах | Директива Next.js, запрещающая кэшировать страницу между разными посетителями — каждый заход рендерится заново на сервере. Новая страница `/resources/new` объявляет её явно (комментарий в файле ссылается на то же правило, что уже стоит у `/notifications`/`/purchases`/`/settings`): личные данные на минутном кэше показали бы одному человеку остаток чужой сессии. |
| `role="tablist"` + контент всех панелей в HTML одновременно | Паттерн вкладок, где переключение происходит на клиенте (`useState`), но **все** панели всё равно отрисованы сервером и лежат в HTML — неактивные просто скрыты атрибутом `hidden`. Выбран (`ProfileTabs.tsx`) специально, чтобы не делать страницу профиля динамической через `searchParams` (тот самый урок 11.09 про `/portfolio/[slug]`) и чтобы поисковик видел содержимое всех вкладок, а не только первой. |
