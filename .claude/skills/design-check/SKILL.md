# Design Check

Проверка текущего diff (`git diff`, плюс новые нетреканые файлы через `git status`) на соответствие правилам из `docs/DESIGN.md`. Не спрашивать, что проверять — сам смотреть изменённые `.tsx`-файлы в `src/`.

## Порядок действий

1. Прочитать `docs/DESIGN.md` целиком (если ещё не прочитан в этой сессии) — правила ниже кратко продублированы, но `docs/DESIGN.md` первичен, при расхождении верить ему.
2. Посмотреть `git diff` и список новых файлов — собрать список реально изменённых/новых `.tsx`/`.css` файлов.
3. По каждому файлу пройтись по чек-листу:

### Цвета

- Используются только `orange` (primary), `blue` (secondary), `lime` (tertiary) как акцентные цвета. Никаких `emerald`, `violet`, `green`, `purple` и т.п. — если такой цвет встретился, это нарушение. **Исключение — `red`:** узаконен 2026-07-28 как служебный цвет ошибок и разрушающих действий (текст ошибки под полем, плашка ошибки формы, удаление из корзины). В декоре и бейджах его быть не должно.
- Кнопки/CTA — **по умолчанию orange или нейтральный** (secondary-кнопка без фона). Кнопка **может** быть blue/lime через `colorClassName`, когда цвет несёт смысл секции (решение владельца 2026-07-28 — прежний запрет отменён). Проверять не цвет, а количество: **на одном экране один главный CTA**, остальные разноцветные кнопки — второстепенные действия внутри своей секции.
- Нейтральная палитра — `zinc`, не `gray`/`slate`.
- "Белый" фон — только `bg-[#fbfbff]`, никогда `bg-white`.
- Тёмный текст — `zinc-950` (заголовки), `zinc-600`/`zinc-700` (тело), `zinc-500` (второстепенный).

### Компоненты

- Все кнопки собраны через `src/components/Button.tsx` (`variant="primary"|"secondary"`, `size="sm"|"md"|"lg"`) — не собраны вручную из `<button>`/`<a>` с Tailwind-классами россыпью.
- Стрелки-кружки — только через `src/components/ArrowCircle.tsx`, не пересобранный SVG в новом месте.
- Async/ещё не готовый контент — через `src/components/Skeleton.tsx`, не пустой div и не спиннер.

### Типографика

- H1 (заголовок страницы) — `text-4xl font-extrabold tracking-tight sm:text-5xl` (кроме Hero на главной — у него свой крупный размер).
- H2 (заголовок секции) — `text-3xl font-bold tracking-tight sm:text-4xl`.
- H3 (заголовок в карточке) — `text-lg font-semibold`.
- Основной шрифт — Plus Jakarta Sans (через `--font-sans`), не новый шрифт без причины.

### Вёрстка

- `<main>` страницы портфолио-части — `mx-auto max-w-6xl px-6`. **Исключение — маркетплейс:** он шире (до 1920px, паддинг до 120px), это осознанное решение 2026-07-26, а не нарушение.
- Радиусы: карточки — `rounded-2xl`/`rounded-3xl`; кнопки/бейджи/навбар — `rounded-full`.
- Вертикальный отступ секций — `py-28` на десктопе, **с уменьшенным мобильным вариантом** (`py-16 sm:py-28` и т.п.). Фиксированный `py-28` без `sm:`-шага — нарушение, это чинили сплошным проходом в responsive-паcс.
- Свечение-градиент на hero — только через `src/components/PageGlow.tsx`, руками не собирать (было семь разъехавшихся копий). `overflow-x-clip` вешается на полноширинный родитель, `max-w-*` — на обёртку контента внутри него.
- Анимации появления при скролле — переиспользуемый `src/components/FadeIn.tsx` (IntersectionObserver + CSS-переход), **не `motion.div` с `whileInView`**: Motion сознательно снят с лендинга ради веса бандла и остаётся только там, где есть настоящий жест или анимация высоты (`PageTransition`, `PortfolioHero`, `ClientReviews`, `Navbar`, `FaqAccordion`, `Hero`, `AuthorCta`).
- **`dark:`-классы — живой код, вычищать их НЕЛЬЗЯ.** Тёмная тема работает с 2026-07-17 (`ThemeProvider.tsx` ставит класс `.dark` на `<html>`). Проверять надо обратное: у нового компонента `dark:`-варианты **есть** и построены по правилу инверсии из `DESIGN.md` (белый фон → `zinc-950`, текст `zinc-950` → `zinc-50`, акценты — отражение вокруг шага 500). Исключение — цветные поверхности (primary-кнопка, бейджи поверх фото): у них `dark:`-вариантов нет намеренно.

## Формат ответа

Кратко, по пунктам — только реальные нарушения (не хвалить за то, что "всё ок" по каждому пункту чек-листа, если нарушений нет вообще — одна строка "нарушений не найдено"). На каждое нарушение:

- файл и строка;
- что не так;
- какое правило `DESIGN.md` нарушено;
- конкретная предлагаемая правка (не только "поправь", а именно что заменить на что).

Не переходить к исправлению файлов без подтверждения пользователя — только отчёт.
